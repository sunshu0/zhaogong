# 性能预算

每个页面在能用之前，浏览器要先下载一批 JavaScript（首屏 JS）。这份预算给每个路由定一个上限，页面越写越重时能马上发现（#169）。

## 量的是什么

- **每个路由首屏要下载的 JS，gzip 压缩后的大小**（KB，1 KB = 1024 字节）。压缩后的大小接近用户实际下载的量。
- **路由用到哪些 JS 文件，读构建自己的统计：** `.next/diagnostics/route-bundle-stats.json` 里每个路由的 `firstLoadChunkPaths`（Next 16 每次构建都会生成）。每个文件只算一次，用 Node 自带的 gzip 压缩后相加。
- 不含图片、字体、CSS 和页面的 HTML / RSC 数据，也不含点开以后才加载的部分（弹层、聊天等按需加载的代码）。
- 正式构建（`npm run build`）和测试构建（`npm run e2e:build`）量出来一样大（10-18 实测），用哪个都行。

## 怎么跑

```bash
npm run build
node scripts/perf-budget.mjs
```

测试构建在 `.next-e2e`，加 `--dir .next-e2e`。会列出每个路由的大小和预算，最重的在前；有一个超了，退出码就是 1。现在不在 `npm run check` 里，因为它要先构建；门槛跑完测试构建之后顺手跑一次。

## 预算是怎么定的

- **2026-10-18 在 main `b1439f4` 上实测，每个路由加 12% 余量，向上取整到整 KB**，写在 `scripts/perf-budget.json`。没有为了过线改过任何页面。
- 当时最重的是 `/me`（214.3 KB），最轻的是 `/employer` 和 404 页（155.2 KB）。职位列表 `/jobs` 186.6 KB，首页 185.6 KB。所有路由都要的那部分：框架和 React 约 128 KB，加上全站的顶栏、底部导航等约 155 KB，也就是最轻的那几页的大小；各页面自己的代码在这之上多出 0–60 KB。
- **2026-10-19 第 20 轮（中英切换）重写过一次**，按 `t/round20` `841635a` 的测试构建实测加 12%（导师决定）。每个页面多出 30–60 KB：字典的中文、英文两份都进了首屏 JS，所有页面都要的部分从约 155 KB 涨到约 187 KB，`/me` 从 214.3 涨到 269.7 KB。另开了 Issue「客户端只下载当前语言的字典」，排在第 20 轮合并后第一项，做完再按实测往下改。
- **2026-10-19 #240 之后又重写了一次**：按 `t/240` `91d7dc6` 的测试构建实测，加 12%。浏览器现在只下载当前语言的字典，34 个路由里有 33 个变轻了，中位数少了 11.4 KB，最多的是 `/admin`，少了 21.7 KB；`/employer/post` 从 274.3 KB 降到 258.0 KB，`/me` 是 256 KB，最大的预算从 308 KB 降到 289 KB。还没回到第 20 轮之前的水平（`/me` 214.3 KB）：中文那一份字典、语言切换和 `LangProvider` 还在首屏里。
- **新路由**还没写进预算时，按默认值（现在最大的那个预算，289 KB）算，表里标「未设预算，按默认」。合并前用 `--write` 把它写进去。

## 超了怎么办

1. 先看是哪个路由、多了多少。多出来的一般是新引入的依赖，或者把只在点开后才用到的组件放进了首屏。
2. 能拆的拆：只在用户点了之后才用的东西（弹层、编辑器、图表）改成按需加载；大的依赖看有没有更小的替代。
3. 确实需要变重（新功能本来就要这些代码）：`node scripts/perf-budget.mjs --write` 按新的实测值重写预算，在 PR 里写明哪个路由多了多少、为什么。审 PR 时看这一条。

`--write` 会重写所有路由的预算，所以只在确认别的路由没有意外变重时用。

## 文件

- `scripts/perf-budget.mjs`：读构建统计、算大小、对比预算、打印表格。
- `scripts/perf-budget-rules.mjs`：算大小和比较的规则，单测在 `perf-budget-rules.test.mjs`（`npm run test` 里）。
- `scripts/perf-budget.json`：预算（`margin` 余量，`defaultKb` 默认值，`routes` 各路由的 KB 数）。

## 主要点击的交互延迟（#418）

除了首屏大小，再用固定实验测手机上五个主要操作：职位卡、详情「立即沟通」、聊天发送、「更多」和筛选弹层。每项五次，375×812、触摸、Chromium CPU 4×，报告中位数和最差，对照 200 ms。**超时只提示；采集失败或数据不完整才退出非零。**

这不是整页真实用户 INP，也不是异步网络请求完成时间。Event Timing 从输入等待、事件处理量到下一次绘制；测试另确认页面、消息或弹层确实出现。定义和限制见 [ADR 0049](adr/0049-interaction-budget.md)。

按机器资源规矩取得对应构建 / inp 时段后运行：

```bash
npm run e2e:build
E2E_PORT=8705 npm run perf:inp
```

PowerShell 中第二行写成 `$env:E2E_PORT='8705'; npm run perf:inp`。端口必须空闲：Playwright 自己启动并在结束时关闭生产测试服务器，不复用任何现有服务器。默认端口是专用门槛端口 8705；独立诊断按分配使用其他端口。缺少 `.next-e2e/BUILD_ID`、误指定开发模式或端口被占用都会失败。不要用验收页的开发服务器替代。

控制台打印汇总，`test-results/inp.json` 留每个样本的可信目标事件、Event Timing 原始记录、时间窗口、interactionId 对应证据和前后校准。校准点击由测试注入，故意慢 48 ms，不算目标样本。能力缺失 / 采集链路坏了不能当作快；只有同文档前后校准成功、目标事件完整且没有达到记录阈值时，才以显式 `below-threshold` 状态记录 16 ms 上界。硬导航丢失旧文档数据会报错。

总导师 R2 已批准在 e8 后加独立 inp 段，仍只提示。拿共用 GPU 锁、最多 15 分钟，空闲至少 3.5 GB 间隔 30 秒读两次，owner command 标 inp；前 3 次必须同时记录进程树峰值内存、时长和其他并发活动。超过 10 分钟或 1.5 GB 先报总导师。

首次实测数字及头三次资源花费尚待本实现运行后据实填写；实现完成不等于门槛通过。不要用旧草稿的测量结果验收新代码。纯函数回归在 `scripts/perf-inp-rules.test.mjs`，由正常 `npm run test` 收集。

# 0053 — 聊天列表：分组和置顶

状态：第 1 块已合并（隐私页那句用户 2026-10-30 同意）；第 2 块「标为未读」提议（2026-10-31，设计导师 2026-10-30 认可）。

## 情况

老板一天回几十个人，聊天列表只有一串按时间排的会话（`MessageWorkspace.tsx`）。用户批的单子 C7：列表加置顶、标记未读，按「新招呼 / 沟通中 / 已约面」分组。

## 决定

**分组**从「我这一边」算，求职者和企业同一套，一个会话只进一组，从上到下先符合先进（`chat-list.ts`）：

1. 已约面：这个求职者在这个职位上的申请有还有效的面试邀约（`interviews.status` 是 proposed、confirmed 或 counter，`LIVE_INTERVIEW`）。取消、婉拒了就回到下面两组。
2. 新招呼：对方说过话（消息，或发起交换），我这一边一句没回过（没发消息、没发起交换、没答应或拒绝对方的交换）。企业一侧「我」是整个团队，和已读一样。
3. 沟通中：其余的，包括我先开口、对方还没回。

「已约面」要服务端给：共享会话的读取（`readShared`）和每 10 秒的变化（`listSharedChanges` 的 heads）都 left join `job_applications`（`seeker_email, job_id` 唯一索引）再 join `interviews`（`application_id` 唯一索引），每个会话最多一行，查询计划是两次 SEARCH USING INDEX。heads 每次都整份给（`SharedChanges.interviews`，同 ADR 0044 的 `paused`），因为发邀约、取消都不改会话的 `updated_at`。审核员对话（ADR 0046）不进分组，照旧固定在最上面。

列表顶上原来那行「最近联系 · N 个会话」换成一行筛选按钮「全部 / 新招呼 / 沟通中 / 已约面」，各带个数，默认全部；标题留给读屏。这样手机上不多占一行，也不加分组标题。

**置顶**存在身份自己的 ChatRecord 里（`pinned`：会话 id → 置顶时间，最多 10 个），不加表、不加迁移：

- 求职者每个账号一份（`chat_records`）；企业一侧整个团队共用一份（`team_chats`，#87），和已读状态一样，一个同事置顶，同事都看到。对方永远看不到：置顶不写会话表，共享会话的改动也不走共享那条路。
- 改动照旧一条一条发到服务端（`ChatChange` 的 `pin`），服务端在当前记录上应用。记录现在是**条件写**（ADR 0031）：读的时候带上行的 `updated_at`，写的时候 `where updated_at = 读到的`，被别人先写了就重读重算（`untilSettled`，最多三次）。这样两个同事同时置顶，后写的不会把先写的整份盖掉。这对所有写自己记录的改动都成立（消息、举报、交换），不只置顶。`updated_at` 每次写都往后走至少 1 毫秒，同一毫秒的两次写也分得清。
- 置顶的排最前（置顶时间新的在前），筛选到一组时组里置顶的也在前。行里时间前面一个图钉，不加行高。在会话里「更多」菜单置顶、取消置顶。满 10 个再置顶，提示先取消一个。
- 指向已经不在的会话（对方删号、企业最后一位成员删号）的置顶，读的时候不算，下次写时清掉。
- 删号、导出跟着 ChatRecord 走：求职者的 `chat_records` 删号时删、导出里有；企业的 `team_chats` 在最后一位成员删号时删，导出照旧不带企业的聊天记录。

**标为未读**（第 2 块）也存在 ChatRecord 里（`unreadMarks`：会话 id → 标记时间），归属、条件写、删号和导出都和置顶一样，没有上限（只认列表里有的会话，导入时算进会话数上限）：

- 在会话「更多」菜单点「标为未读」，回到列表，这一行右边数字角标的位置换成一个圆点，名字加粗，不加行高。读屏读「已标为未读」（状态，和菜单那项的动作分开）；焦点落在这一行（「返回」也是），不掉到页顶。
- 只是一个标记，**不改已读时间**：改了会让对方的「已读」变回去，等于告诉对方。改动 `unreadMark` 和置顶一样只写自己的记录，不走共享那条路。
- 圆点**不算未读消息**：行里的数字、页面上的「N 条未读消息」、标签页标题、导航角标都只数真消息。有真未读时照旧显示数字，不显示圆点。
- 再打开这个会话就清掉：浏览器的 `markRead`（有标记时也发「read」），服务端两条「read」路径（自己记录里的会话、共享会话的 `markSharedRead`）都在自己的记录里清掉标记。刚标完、地址还指着这个会话时（手机的返回是异步的），不当作又读了一次。

## 后果

- 隐私页「聊天：」那条加一句（中英文），说置顶、标为未读存了、只给自己排列表、企业团队共用一份。用户 2026-10-30 同意，第 1 块已整句加上，第 2 块不再改。
- 共享会话的数据（`SharedConversation`，「数据与账号」导出里的 `sharedChats`）多一个 `interview` 布尔值。
- 一个记录的写入在别人同时写时会多读一两次；三次都被抢先就报错，浏览器的待发箱稍后再发（改动有票，只应用一次）。

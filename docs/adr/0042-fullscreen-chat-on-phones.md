# 0042 手机上打开的对话占满整屏，开着哪段写在地址里

- 状态：提议（执行 B local_74f69b45 起草，等导师 local_573a9208 审；说明 `zg-scratch/mentor-573a/brief-B-13.md`）
- 日期：2026-10-26。Issue #397。用户 10-26 19:4x 点名「操作手感 T1–T10」（方案 `plan-boss-gap-feel-visual.md` 第二部分），导师拆成五件，这是第一件 T1。

## 情况

手机上（1024 px 以下）打开一段对话，聊天还挤在网页里：上面是站点顶栏、「求职聊天」标题和未读行，下面是演示说明、页脚和底部导航，375×667 的屏幕上消息区只剩一小块。返回是组件里的状态：手机的返回键直接离开 /messages，刷新以后回到列表。输入框固定 3 行；键盘弹出时，Android 的 Chrome 默认只缩小「看得见的那块」，页面高度不变，底部的输入区可能被挡住。

## 决定

### 1. 整屏：对话盖在页面上，站点的东西藏起来

1024 px 以下打开一段对话时，`MessageWorkspace` 的聊天区加 `data-chat-open`，自己变成 `fixed`、贴满窗口（高 `100dvh`，有 `visualViewport` 时用它的高和上边，见第 4 条；留出刘海和底部横条的安全区）。`globals.css` 用 `:root:has([data-chat-open])`（同一媒体查询里）把站点顶栏（`[data-site-header]`）、页脚（`[data-site-footer]`）、底部导航（`#bottom-nav`）设成 `display: none`，底部导航让出的空白归零，页面本身不滚。工作台的标题、未读行和下面的说明也只在这时藏起来。说明里「消息保存在服务器上，双方都能看到……」是在告诉用户数据怎么处理，和隐私页对得上，整屏时也要看得到（导师 21:2x 裁定）：手机上它是消息区最上面的一行灰色小字，跟着消息一起滚，不固定占位；1024 px 起照旧在聊天区下面。演示账号的演示说明照旧只在下面。

为什么用 CSS 而不是在 `BottomNav` 里判断：底部导航按路径决定藏不藏（`hidesBottomNav`），可是「开着哪段对话」在查询参数里，而且只有聊天区自己知道这段对话找没找到（地址里的编号可能不在这个身份的会话里）。由聊天区标一个属性、样式表跟着它，开着就藏、关了就回来，服务端渲染和脚本没跑完时也一致，也不用改 A 线正在改的 `nav.ts`、`BottomNav.tsx`。用 `display: none` 而不只是盖住：盖住的东西读屏软件还会念、Tab 键还会走到。`:has()` 不支持的旧浏览器，对话照样盖满整屏，只是底下的东西还在。

对话列表（没打开对话时）照旧：顶栏、底部导航、页脚都在。1024 px 起列表和对话并排，什么都不变。

### 2. 返回键：开着哪段写在地址里

开着的对话就是地址里的 `?conversation=<编号>`（原来只在进来时读一次，现在一直以它为准，`useOpenConversation`，`fullscreen-chat.ts`）。用 `history.pushState` / `replaceState`（Next 16 跟着它们更新 `useSearchParams`，不重新请求页面）：

- **手机上从列表点开**：`pushState`，加一条历史记录。手机的返回键回到这条之前，就是列表，还在 /messages。
- **顶栏的「←」**：如果当前这条就是刚才点开时加的（地址和历史长度都对得上），`history.back()`，和返回键一样；不是（从别的页面的「立即沟通」直接进来、刷新过、后来又绕回同一个地址），`replaceState` 换成列表的地址，不往回退，免得退出 /messages。
- **桌面上点列表**：`replaceState`，只换地址、不加历史记录，桌面的返回键和改之前一样。
- 刷新后还在这段对话里。

「刚才加的那条」记在模块变量里，不记在 `history.state`：Next 之后更新路由时会用自己的状态整份换掉它。

直接进来的那种，手机返回键回到来的页面（职位页等），和别的 App 从通知点进对话再按返回一样；只有「←」保证回到列表。

### 3. 输入框随内容长高

手机上从 1 行起，最多约 5 行（`max-h-36`：五行 1.5 rem、上下内边距和边框），超过在框里滚。用 CSS `field-sizing: content`；不支持的浏览器（Firefox、旧 Safari）每次改字时按 `scrollHeight` 设高度。「＋」、输入框、「发送」本来就底边对齐（`items-end`）。1024 px 起照旧固定 3 行高，桌面不变。

### 4. 键盘

/messages 这一页的 viewport 加 `interactive-widget=resizes-content`（页面里导出 `viewport`，和布局的合并）：支持它的浏览器（Android 的 Chrome）键盘弹出时整页变矮，盖满窗口的聊天区跟着变矮，输入区贴在键盘上面。只加在这一页：全站加的话，别的页面填表时，贴底的固定栏（底部导航、职位页的「立即沟通」栏）会跟着键盘顶上来，挡住正在填的地方。

不支持它的（iPhone 的 Safari）只缩小「看得见的那块」，页面还可能被推着滚。兜底：对话开着时听 `visualViewport` 的 `resize` 和 `scroll`，把它的高和上边写进聊天区的 `--chat-height`、`--chat-top`。消息区变矮时（键盘、输入框长高），原来在看最新一条的，跟着滚到底（`MessageLog` 里的 `ResizeObserver`）。

### 5. 消息区要大

375×667、键盘收起时，消息区至少占屏高一半。顶栏、职位横条、雇主标记、活跃度、常用语这些都不删、文字不改，只在手机上收紧一点：对话顶栏上下内边距 12 → 8 px，输入区 12 → 8 px，雇主标记一行 8 → 6 px。活跃度那行照旧换行，不改成横着滚（`chat-activity` 测试要求不截断）。

## 后果

- 手机上从列表点开对话会多一条历史记录；桌面不会。
- 测试：在打开的对话里要用顶栏（账号菜单、切换身份）或底部导航的 e2e，手机上先按「←」（`leaveFullscreenChat`）；在打开的对话里看未读数，手机上看标签页标题（#291 的「(n) 」，`expectChatUnread`）。新测试 `e2e/chat-fullscreen.spec.ts`。
- 以后别的整屏流程（比如拍照、填长表）也可以照这个办法：标一个属性，样式表藏站点的东西。

## 没选的

- **改 `hidesBottomNav` 按路径加参数判断**：只管得了底部导航，顶栏和页脚还要另想办法；而且编号不对时会把列表的底部导航也藏了。
- **单独的路由 `/messages/<编号>`**：返回键自然就对，但要搬页面、改所有链到 `?conversation=` 的地方（通知、待办、推荐人才、申请人……），桌面并排时也要两个路由共用一个布局。这件只改布局和交互，不值得。
- **整站加 `interactive-widget=resizes-content`**：见第 4 条。

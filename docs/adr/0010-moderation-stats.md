# 0010 审核数据：每次请求时从整张表算，记下举报的处理时间

- 状态：已采纳
- 日期：2026-10-16（#70，R-34）

## 情况

第 15 轮要求在审核后台显示审核数据：现在待审的职位和未处理的举报，最老的一条等了多久；最近 8 周每周的新举报、处理完的举报、从提交到处理的中位用时、下架职位数、封禁企业数。

在这之前：

- `reports` 表只有提交时间 `created_at` 和状态，**没有关闭的时间**，算不出「提交到处理」的用时；
- 下架、驳回、封禁和通过都写进 `moderation_log`，带时间（`at`）；封禁一并下架了几个职位记在 `taken_down`；
- 数据量很小：演示数据十几条举报，线上刚开始时一周也就几十条。

## 决定

1. **记下处理时间。** 迁移 0008 给 `reports` 加可空列 `handled_at`（不用 SQL `DEFAULT`，和 ADR 0005 的约定一致）。`updateReport`（`src/lib/data.ts`）把举报关闭时写入当时的时间，重新打开时清空。审核后台的下架、驳回、封禁都经过它。迁移之前已经处理的举报没有这个时间：不补、不猜，统计里不计入用时，页面上写明有几条。
2. **每次请求时算。** `getModerationStats()`（`src/app/[lang]/admin/stats-actions.ts`，先 `requireModerator()`）读出这个市场的全部职位、举报和审核记录，交给纯函数 `moderationStats`（`src/app/admin/moderation-stats.ts`）算。周按新西兰时间、从周一算起；中位数取当周关闭的举报。纯函数有单测，不用数据库。
3. **不加图表库。** 8 周的数字用表格，新举报一列加一条 CSS 宽度的横条，和雇主的职位数据（#55）一样。

## 后果

- 数字和审核队列用的是同一份数据，审核员每处理一条，页面马上重新取一次。
- 每次打开审核后台要读整张 `reports` 和 `moderation_log`。现在没有问题；**数据多了以后**，按这个顺序改，前一步不够再做下一步：
  1. 只读 8 周以内的行：给 `reports.created_at`、`reports.handled_at`、`moderation_log.at` 加索引，查询带上时间下限（当前打开的举报和待审职位另外按状态查）；
  2. 计数改成 SQL 的 `GROUP BY` 按周汇总，中位数仍在代码里对当周的用时排序（一周的行数不会很多）；
  3. 再大时，每天汇总一次写进单独的统计表，审核后台只读汇总，当天的部分实时算。
- 按审核员分的处理数用 #60 在审核记录里写的操作人；#60 之前的记录没有操作人，单独列一行「较早的记录，未记审核员」。

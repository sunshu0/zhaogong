## 情况

手机上从职位列表点进一个职位再回来。改之前在 main（`2608872`）上量过，第 10 张卡点进去再回来（375 和 1440 都量了）：

- **浏览器的返回键本来就回到原位**：那张卡离屏幕顶的距离和点进去前一样。Next 把列表页留在页面里（cacheComponents），浏览器自己把滚动位置放回去。
- **页内的「← 职位列表」回到最上面**：它是一次新的跳转（`router.push`），新跳转都从顶上开始。外部职位页的「← 实习 / 专业职位」也一样。

## 决定

### 1. 列表外面包一层 `ListPlace`（`src/components/seeker/list-place.tsx`）

包在职位列表（含宽屏的预览栏）和实习、专业职位的列表外面，不加元素（`display: contents`）。列表里的链接被按下（`pointerdown`；键盘和读屏走 `click`）时，它在本标签页的 sessionStorage 记一条：哪个列表（路径加筛选）、哪个链接、它那张卡离窗口顶多远、页面滚到哪。只记最近一条。规则（读这一条、该回哪个列表、卡没了回哪）在 `list-place-core.ts`，有单元测试。

### 2. 「←」从哪个列表来就回哪个列表的原位

「← 职位列表」（`BackLink`）和外部职位的「← 实习 / 专业职位」（`SectionBackLink`）点的时候先看记的那条：当前页就是从那个列表点进来的，就跳回那个列表（筛选也在），`scroll: false`，并告诉列表「这是回来」（`markReturn`）。列表渲染出来后把同一张卡放回同一个高度；那张卡没了（职位下架了），就回到原来的滚动位置，超出页面就夹在页内。等卡最多 5 秒，用户先滚动或按键就不动了。

- 不是从列表来的（分享链接直接打开、从别处来），照旧回到 `/jobs`（上次的筛选）顶上。
- 浏览器返回键不管：它本来就对，再插手反而会和浏览器抢。
- 「←」照旧是一次新的跳转，不改成 `history.back()`：要保留向后滑的转场（#171）；历史里多一条，和以前一样。
- 从别处（底部导航「职位」）进列表，照旧从顶上开始。

### 3. 按下就预取（T4）：试过，这次不做

做法是：手指按住 80 ms 没移动、或没移动就抬起（鼠标按下就算），调 `router.prefetch(href, { kind: "full" })` 取整个职位页，手指划过去滚动不取。

在 test build 上实测（f4，10-27 13:51，手机和桌面一样）：按下约 80 ms 后发出的是 Next 的「运行时预取」（请求头 `next-router-prefetch: 2`），松手点完照样再发一次整页请求。原因：开了 cacheComponents 和 partialPrefetching 以后，预取最多走到「运行时」这一层，碰到没缓存的读取就停在 Suspense 那里；职位页的职位是直接读数据库的，没有 `"use cache"`，所以预取取不到职位，点完还得等它。也就是说，按下就预取没有实际的提前量，只多一个请求。

要做到，得给职位页的职位数据加短缓存（`"use cache"` 加几十秒的寿命）。代价是审核员下架职位、封禁企业以后，最多晚缓存寿命那么久才生效，还要核对 D1 在缓存里能不能用。这是安全上的取舍，要用户定（导师已写进看板「等用户决定的事」），不在这次做。

## 不做的

- 分页（职位过 300 个再说）；共享元素飞过去（放到最后再看）。
- 收藏、「我的申请」：页上没有回它们的「←」，浏览器返回键本来就对。
- 聊天的列表（执行 A 在做 #407）。
